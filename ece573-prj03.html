I. Objective

In this project, you will add authentication and authorization to the persistent marketplace. You will explore how a separate login service issues JSON Web Tokens (JWTs), how the marketplace verifies them, and how one shared wrapper can protect several REST routes.

The baseline uses these scripts to reset the database and signing key, start Postgres and two Go services, register two accounts, grants credit, list and order an item, and finally restart the marketplace service to make sure the order succeeds.

Open 'docker-compose.yml' to understand the architecture of our marketplace with added support of authentication and authorization. It defines three services: postgres and marketplace-service similar to that of Project 2, and a login service to authenticate users. The two Go services are built from separate targets in the root Dockerfile so that both can use the shared 'auth' package, which takes care of handling JWTs.

Read the source files for the login service. The login service owns registration, password verification, and JWT issuance. Registration creates an account with zero credits and a regular-user role. The supplied helpers hash passwords with Argon2id and sign JWTs using an Ed25519 private key. It creates 'course-admin' on startup if the account doesn't exist and updates the password based on 'secrets/admin-password', which may be regenerated randomly by the reset script. Then, the login service will serve two RESTful endpoints, POST /accounts for registration and POST /login that issues a JWT Bearer token upon successful login. Follow-up RESTful requests should include the JWT to identify the user.

Since we haven't implemented authorizations in the marketplace service yet, run_baseline.sh sets the environment variable AUTH_ENABLED=false so that the first run could proceed without triggering the unfinished authorizations. III. Authorization Implementations

The marketplace service retains four RESTful endpoints from Project 2, including GET /listings, POST /listings, POST /orders, and GET /accounts/{account_id}, and also adds POST /accounts/{account_id}/credits. While anyone can use GET /listings, only specific users can access the other four when AUTH_ENABLED=true. In short, only regular users may list or buy, users may only view their own accounts, and only the admin may grant positive credits to regular users.

Read 'marketplace-service/main.go' first to see the route table. It includes all routes when AUTH_ENABLED=false, and one route for AUTH_ENABLED=true as the example. A 'TODO Project 3' comment indicates that you will need to complete the other three routes requiring authorizations based on the example. Without knowing the detail of the authorization wrapper 'requireAuthorization', please make reasonable guess on its parameters and then complete this TODO item.

Now we are ready to review 'marketplace-service/authorization.go' to understand and implement the authorization wrapper 'requireAuthorization'. This function uses the decorator pattern as we have introduced in the lectures to add authorization to any RESTful handler function ('http.HandlerFunc'). The supplied code extracts the JWT token from request header and verifies it. The 'TODO Project 3' requires you to write a few lines of code to check whether the token's subject and role are permitted using the filters 'matchesID' and 'allowsRole', before proceeding to the requested marketplace operation 'next'. Make sure to generate specific error response for failures: return HTTP 400 ('http.StatusBadRequest') if the filter reports an invalid identity field, and return HTTP 403 ('http.StatusForbidden') if the operation is not permitted.

After you have completed both Project 3 TODOs, run acceptance.sh and attack.sh to verify the correctness.

The acceptance script checks successful registration, an admin credit grant, listing, public browse, and checkout. The attack script numbers its ten rejection tests:
  1. Wrong-password login (401).
  2. A regular user cannot grant credits (403).
  3. Admin cannot grant credits to an admin account (400).
  4. A missing token cannot create a listing (401).
  5. An invalid token cannot create a listing (401).
  6. Bob cannot create a listing for Alice (403).
  7. Admin cannot create a listing (403).
  8. Alice cannot place an order for Bob (403).
  9. Admin cannot place an order (403).
  10. Alice cannot read Bob's account (403).
