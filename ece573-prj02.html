The above output from run_baseline.sh shows a lot of details on our persistent marketplace. It consists of two services marketplace-service and postgres, each running in its own container. The marketplace-service service uses the source code in the 'marketplace-service' directory. On the other hand, the postgres service uses a pre-built Postgres image, which saves us a lot of effort. Instead of managing these two containers individually, we utilize Docker Compose to orchestrate the two so that they can be easily built, started, and stopped as a whole.

Docker Compose uses the 'docker-compose.yml' file to define the services as containers and how they should be orchestrated. Open 'docker-compose.yml' and you should be able to tell it defines two services. The first service is postgres that uses the pre-built image 'postgres:16-alpine'. More details of this image can be found on Docker Hub, including the descriptions for the environment variables defined in the postgres service. The second service marketplace-service should be built from the directory 'marketplace-service'. The port '8080' is published as '8080' so that we can access the service inside the container from the VM.

What is not shown in the docker-compose.yml script is that by default Docker Compose will create a private network to interconnect the containers. Each container gets its own IP address and will need to know the addresses of others before they can communicate. For example, how could the marketplace-service service know the address of the postgres service? It is definitely not a good idea to hard code the addresses in the script and in the source code. Instead, we utilize the DNS service provided by Docker Compose where each service container has a domain name matching the name of the service. We pass 'postgres' via environment variable to the marketplace-service so marketplace-service can use it to connect to the database.

Our script start.sh (called by run_baseline.sh) uses docker compose up -d --build to build the container image for marketplace-service and then start both services. This helps to avoid the common error where the code for marketplace-service is updated but the service runs an older version of the container image. As shown by the output of run_baseline.sh, it may take a few minutes to complete for the first time as it needs to pull images from Docker Hub. Later on, it will take less time to start.

III. REST API Implementations

Now you should spend some time reading the Go source code in the 'marketplace-service' directory to understand how the RESTful service is implemented. We have discussed them in the lectures and the README.md provides a quick summary as well. You will need to complete two intentionally incomplete functions for this section: Balance Transaction and Account Assembly.

For Balance Transaction, locate the function 'CreateOrder' from the file 'marketplace-service/marketplace/orders.go'. This function is complicated as it needs to handle rows from multiple tables for a transaction, and you should focus on the part starting with 'TODO Project 2' to make the modifications. It should take fewer than 10 lines of code to complete the balance check and to return the required error.

For Account Assembly, locate another 'TODO Project 2' in the function 'GetAccount' from the file 'marketplace-service/marketplace/accounts.go'. You will need to follow the existing code as an example to call each of the three helpers ('getListingsBySeller', 'getOrdersByBuyer', and 'getSalesBySeller'), return immediately on an error, and assign the resulting activity fields. It should take fewer than 50 lines of code.

Once you have implemented both functions, follow README.md to verify the correctness by running acceptance.sh.
