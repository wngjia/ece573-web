I. Objective

In this project, you will learn the basics of Apache Cassandra, a popular open-source distributed NoSQL database. A three-node Cassandra cluster is integrated into our shopping marketplace to serve listing views and completed-order history, while Postgres still owns account credentials and balances, as well as listing and order states.

While production Cassandra deployment will use multiple physical servers, we use Docker Compose to create a Cassandra cluster via container orchestration for development and testing.

To manage the database system consisting of these programs, Cassandra provides two tools, nodetool to access the statistics of the Cassandra programs, and cqlsh to manage the databases and the data via the Cassandra Query Language (CQL), which is very similar to SQL. For simplicity, we don't install these two tools in our VM but use them directly from the Cassandra containers. Use docker compose exec to execute a program in a container. III. Marketplace Integration

Cassandra supports a lot of programming languages, including Go, via CQL and a set of APIs. For Project 4, we provide the history package in marketplace-service to demonstrate how to create keyspaces and tables, and how to write data to and read data from a Cassandra cluster in Go.

Take a look at 'marketplace-service/history/history.go'. This file includes functions to connect to the Cassandra cluster with the given consistency and seed, and to create the keyspace marketplace_history requiring 3 replicas in 'datacenter1' as well as four tables. Among the four tables, both purchases_by_buyer and sales_by_seller contain exactly the same information for a completed order but with different keys to facilitate different queries: purchases_by_buyer is partitioned by buyer ID so queries by buyer as purchases can be queried within one partition, and sales_by_seller is partitioned by seller ID so queries by seller as sales can also be queried within one partition. Both tables use 'order_day', 'ordered_at', and 'order_id' as the clustering key that further support date/time ranged queries. The other two tables listings_by_seller and available_listings tables support different ways to access the listings, either by seller ID or as a whole for unsold items.

The functions provided by the other two files in 'marketplace-service/history' are used by the RESTful handlers in 'marketplace-service/handlers.go'. Both the Postgres tables and the Cassandra tables are updated when listings are created and ordered via 'POST /listings' and 'POST /orders'. After Postgres commits a listing or order, the handler writes the updates to Cassandra. Note that if the Cassandra updates fail, the handler will log the failure but still returns HTTP 201 for the committed Postgres operation. On the other hand, for requests to access accounts and listings via 'GET /accounts/{account_id}' and 'GET /listings', most records are obtained from Cassandra tables. In other words, while Postgres still stores the states for listings and orders, Cassandra provides materialized read views to reduce loads on Postgres, but may disagree with Postgres or with each other due to failures and its own consistency guarantees.

IV. Tunable Consistency

According to the CAP theorem, a distributed database like Cassandra must choose one from consistency and availability during a network partition. Cassandra allows to trade-off consistency with availability by tunable consistency where each write and read could choose a different consistency level. For this project we will experiment with the combinations of three consistency levels: ONE for one replica to confirm, ALL for all replicas to confirm, and QUORUM for more than half of the replicas to confirm. A write followed by a read at ONE/ONE can return an older view because the read need not contact the replica that acknowledged the write. On the other hand, all of QUORUM/QUORUM, ALL/ONE, and ONE/ALL overlap in at least one replica to provide consistency guarantee on the same table row when both operations succeed. However, node availability and application behavior still matter and will require your further investigations.

For your convenience, we provide the script 'run_experiment.sh' to streamline the experimental process. This script takes three parameters: the first is the consistency level applies to Cassandra writes, the second is the consistency level applies to Cassandra reads, and the third specifies the number of available Cassandra nodes at start-up. It will reset the data for each run, waits for marketplace readiness, and creates five listings and five orders. Upon completion, it saves only the HTTP status and formatted JSON body of its final 'GET /accounts/Alice' under 'out/experiment-*.txt', and leaves the services running for your inspections.
