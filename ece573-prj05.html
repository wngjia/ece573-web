I. Objective

In this project, you will learn the basics of Kubernetes (K8s), a popular open-source container orchestration platform for cluster computing. We will migrate our Project 4 marketplace from Docker Compose to K8s using a set of Services, Deployments, and StatefulSets for the application and its databases.

While K8s usually runs on a cluster of nodes that are physical servers or VMs in production, we'll create a local K8s cluster with the kind tool, which allows to use Docker container as nodes. In other words, we will have "nested" containers managed by K8s running within Docker containers. On the other hand, since we still manage the local K8s cluster through standard K8s tools like kubectl, all configurations are ready to be deployed into a cluster of physical servers or VMs, either on-premises or in cloud.

IV. Retrying Transient Failures

Project 4 showed that with QUORUM consistency for both read and write, the marketplate service will be able to access the most recent update to any row in the Cassandra read view, as long as more than half of the Cassandra nodes holding the replicas are available.

However, in the case that at least half of such nodes fail, it is possible to have listings and orders committed in Postgres but not projected to the corresponding Cassandra read views. Many of such node failures are not permanent but temporary, e.g. timeouts due to surges of load or the need to run garbage collection, and network interruptions that may heal by themselves. For these transient failures, apparently we could allow the projection code to retry to write to Cassandra multiple times.

How could retrying projections potentially impact our marketplace otherwise? First of all, if we allow to retry the projections as many time as necessary until it succeeds, it may take a long time and anyone sending the RESTful request may have already given up. Therefore, the retrys have to be bounded. Indeed, to avoid anyone to abondon the request when the marketplace takes too much time to process it due to surge of load, we introduce a rate limiter for the requests to our marketplace in 'marketplace-service/request_limit.go'. Nevertheless, since the marketplace service is stateless, we are able to deploy multiple copies of it in K8s to serve more clients via horizontal scaling.

Another issue is how we could test our implementations when transient failures are usually not seen very frequently and happen rather randomly. Instead of waiting for them to happen, we may inject such failures into the system intentionally and observe how the system reacts. Indeed, a simple way to inject a transient failure into a K8s cluster is to kill pods -- K8s will try to maintain the required number of healthy pods and thus replace the killed pods automatically.

Putting everything together, we supply the script run_retry.py to test the retries. It will send 100 uniquely titled listings at 10 new requests per second. After it sends 50 listings, it force-kills 'cassandra-1' and 'cassandra-2', leaving only 'cassandra-0'. K8s will take sometime to replace the two killed Cassandra nodes automatically. In the meantime, with replication factor three, QUORUM writes to the read views need two replicas and will fail. But once the two Cassandra nodes are back online, writes will complete successfully. Experiment with zero retries first, 

ubuntu@ubuntu24:~/ece573-prj05$ ./run_retry.py --retries 0
...

Settle wait: 0s remaining

Saved marketplace logs to /home/ubuntu/ece573-prj05/out/retry-0-marketplace.log

Note that you may see different numbers here in your experiment, or even with failures when creating the listing ('rest_failures') -- this is totally normal as the experimental results depend on the performance of the VM.
